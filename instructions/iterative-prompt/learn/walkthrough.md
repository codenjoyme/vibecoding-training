# Iterative Prompt — Deep-Dive Walkthrough

This walkthrough is the detailed companion to **Part 3** of the Dark Factory Tour module. It explores the `iterative-prompt` brick — why prompts are the new source code, how the UPD/RESULT cycle works, and how to use it as the primary communication channel with the factory.

## Prerequisites

See [module overview](../../coaching/config/modules/010-dark-factory-tour/about.md) for full prerequisites list.

## Part 1: Prompts are the new source code

In a world where yesterday's source code is generated by a model, the prompts that produced it are the real source code. The generated code is the compiled artifact.

Think about it: if you lose the prompts, you lose the *why*. You have code that works, but you don't know why it was written that way, what alternatives were considered, or what constraints shaped the decisions. The next engineer (or the next agent) starts from scratch.

The Iterative Prompt pattern solves this by keeping prompts in version control alongside the generated code:

`
feature-auth/
  main.prompt.md    ← the prompts that built this feature
  auth.py           ← the generated code
  tests/
    test_auth.py    ← the generated tests
`

`git diff` on `main.prompt.md` gives the agent precise context about what changed since the last run. No hallucination, no drift. The agent reads the history and picks up exactly where the last session left off.

---

## Part 2: Team handoff and QA visibility

The Iterative Prompt is not just for solo work. It is a team coordination tool.

**Team handoff:** Engineer A starts a feature, writes 5 UPD blocks, commits. Engineer B opens the same file, reads the history, and continues from UPD6. No context lost. No "what did you do and why?" conversation needed.

**QA visibility:** The QA engineer opens `main.prompt.md` and reads the full decision trail. They understand why the authentication flow was built the way it was, what edge cases were considered, and what was explicitly deferred. They can write better tests because they understand the intent, not just the implementation.

**Cross-IDE:** The prompt file is plain Markdown. It works in VS Code, Cursor, Claude Code, or any CLI agent. The team does not need to use the same IDE.

## Part 3: Write in your native language

The factory processes requests in any natural language. Write in Russian, Ukrainian, English — whatever makes you think fastest.

The model translates internally. Code, CLI calls, and file edits are always in English (because that is what the tools expect). But your requests, your reasoning, your questions — write them in the language where you are most precise.

This is not a workaround. It is intentional. An engineer who writes "сделай аутентификацию через JWT с refresh токенами" is more precise than one who laboriously translates their thoughts into English first. The model handles the translation; you handle the thinking.

## Part 4: One helm-log per feature, one folder per helm-log

**One helm-log per feature or change.** Do not put unrelated work in the same `main.prompt.md`. When you start a new feature, create a new folder and a new prompt file.

Why: the prompt file is the specification for that feature. Mixing two features in one file makes the history unreadable and the context confusing for the agent.

**One folder per helm-log.** Files accumulate around a prompt file:

`
work/
  auth-feature/
    main.prompt.md      ← the helm-log
    auth-spec.md        ← a spec the agent generated
    test-cases.md       ← test cases the agent drafted
    notes.md            ← your own notes
`

The folder keeps everything related to one feature together. The `work/` directory in the factory is the standard location for helm-logs.

## Part 5: The file format and the `go` keyword

The file format is simple:

`markdown
<follow>
iterative-prompt/SKILL.md
</follow>

## UPD1

Your request here. Describe what you want done.
go

### RESULT (UPD1)

What was done. Links to changed files as clickable markdown links.

## UPD2

Next request. go
`

**The `go` keyword** is the signal that you have finished writing the request. Without `go`, the factory assumes you are still typing. This prevents the agent from acting on a half-written request.

**The `<follow>` header** tells the agent which skill files to load on startup. It is optional but recommended — it ensures the agent has the right context before reading the UPDs.

**The `### RESULT` block** is written by the agent after completing the work. It lists every file that was created or modified as a clickable markdown link. It is part of the same atomic git commit as the work — never a separate commit.

A feature implementation can take 1 to 30+ UPD blocks. Each UPD is one atomic unit of work. The agent commits after each UPD, so the git history is a clean record of the feature's development.

---

## Part 6: IDE vs CLI runtime

The Iterative Prompt has two runtimes:

**IDE runtime (VS Code):** The agent runs in the chat window. After each UPD, it re-arms via `vscode_askQuestions` — asking "continue?" before processing the next UPD. This keeps the loop alive without requiring the user to manually ping the agent.

**CLI runtime:** The agent runs as a background process via `orchestrator.py`. It watches the helm-log file for new `## UPD...go` blocks indefinitely. You write a UPD, save the file, and the agent picks it up automatically. No chat window needed.

Both runtimes produce the same output: committed code, committed `### RESULT` blocks, clean git history.

## Understanding Check

1. Why are prompts considered "the new source code"?
   *Because they contain the why — the decisions, constraints, and reasoning that shaped the generated code. Without them, the next engineer starts from scratch.*

2. What does the `go` keyword do?
   *It signals to the factory that the request is complete and ready to process. Without it, the agent assumes the user is still typing.*

3. Why should you write one helm-log per feature?
   *To keep the history readable and the agent's context focused. Mixing features makes the history confusing and the context noisy.*

4. What is the difference between the IDE and CLI runtimes?
   *IDE runtime runs in the chat window and re-arms via vscode_askQuestions. CLI runtime runs as a background process watching the file indefinitely.*

5. Why can you write requests in any natural language?
   *The model translates internally. Writing in your native language makes you more precise. Code and CLI calls are always in English regardless.*
